# Where the data comes from

There is **no downloaded or real dataset**. All data is **synthetic, generated by this code** every run:

- `Seed.java` creates the reference data in PostgreSQL and warms Redis.
- `Generator.java` creates the transactions and sends them to Kafka.

Real card transactions contain cardholder data (PCI DSS), so they can't be shared publicly. Synthetic data is the standard approach for public benchmarks; LinkedIn's 2014 Kafka benchmark used generated records too.

The generator uses a fixed random seed (42), so every run produces the **same 2,000,000 transactions**. That makes runs comparable.

## Reference data (loaded once by `seed`)

| Table | Rows | Fields | How values are chosen |
|---|---|---|---|
| `accounts` | 500,000 | account_id, tier, risk_flag, home_country | Tier: 60% BASIC, 25% PLUS, 12% PREMIUM, 3% CORPORATE. 2% of accounts flagged risky. Country mostly US. |
| `merchants` | 20,000 | merchant_id, name, category, country | 10 categories (grocery, travel, fuel...). About 2% GAMBLING. |

Attributes are computed from the id with a hash function (`Data.java`), so every stage agrees on them without sharing state.

**Redis warm-up:** the first 80% of accounts and all merchants are loaded into Redis. Lookups for the other 20% miss the cache, go to Postgres, and are written back to Redis (cache-aside). In the baseline run the hit ratio was about 97.6%, because popular accounts are among the warmed ones.

## Transactions (produced by `generate`)

One real record from topic `transactions` (key, then value):

```
acct-0236779   {"txId":"47526757-130f-9f52-581c-e1ff0e4ae394","accountId":"acct-0236779","merchantId":"mer-000081",
                "amountCents":113,"currency":"USD","cardBin":404071,"createdMs":1790982561906}
```

| Field | How it's generated |
|---|---|
| txId | Random UUID (seeded) |
| accountId | Power-law pick: low ids are chosen far more often, like real customers where a few are very active (exponent 2.5) |
| merchantId | Power-law pick, more concentrated (exponent 3.0): a few merchants get a lot of traffic |
| amountCents | $1.00 to about $2,500, skewed toward small purchases |
| cardBin | Random 6-digit BIN in 400000-404999 |
| createdMs | Wall-clock time when produced; used to measure end-to-end latency |

Record sizes as JSON: about **180 bytes** in `transactions`, about **360 bytes** after enrichment, about **440 bytes** after scoring.

### Optional skew (hot-partition experiments)

- `WHALE=0.3`: 30% of all transactions come from one account (`acct-0000000`), like a huge corporate customer. Because records are keyed by account, that whole 30% lands on one partition.
- `SALT=4`: the whale's key becomes `acct-0000000_0..3`, spreading it over up to 4 partitions.

## Scaling the data

The size is a parameter: `N=2000000` for 2 million; use `N=10000000` for 10 million. Disk use grows with N (a 2M run used roughly 1 GB of Kafka data across the three topics, plus Postgres, before cleanup), so check free space first.
